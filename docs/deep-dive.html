What it is

A Chrome extension that gives the site in your current tab a security report card when you click it. It runs entirely client-side: no server, no analytics. The only permission that touches pages is activeTab, so it reads a site only when you deliberately scan it, and never in the background.

The five checks

  • Headers and config. CSP quality rather than mere presence, HSTS, frame protection, X-Content-Type-Options, referrer and permissions policy, mixed content, and cookie Secure/SameSite flags. Each finding ships with a paste-ready Express and Nginx fix.
  • Secrets in served JavaScript. Nine known key formats (AWS, Stripe, Slack tokens and webhooks, Google, GitHub, JWTs, private-key headers), plus Shannon entropy over quoted strings 20 to 80 characters long. A string at 4.0 bits per character or more is reported as secret-shaped.
  • Supply chain. Cross-origin scripts loaded without an integrity hash, the gap behind Magecart-style skimming such as the 2018 British Airways breach.
  • Drift. Each scan is stored locally and compared with the previous scan of the same domain. Lost headers, new secrets, new SRI gaps and a lower grade each raise their own finding.
  • ATT&CK mapping. Missing CSP maps to T1189 Drive-by Compromise, missing HSTS or mixed content to T1557 Adversary-in-the-Middle, missing frame protection or SameSite to T1185 Browser Session Hijacking, and missing SRI to T1195 Supply Chain Compromise.

How the grade is computed

One shared scale, so the popup, the toolbar badge and drift detection can never disagree about what a grade means:

src/detectors/headerAnalyzer.ts (excerpt)
weights: high 25  medium 12  low 5  info 2
score  = max(0, 100 - sum of weights)
A+ >= 95   A >= 85   B+ >= 75   B >= 65
B- >= 55   C >= 45   D  >= 30   else F

The bug the unit tests could not see

Live testing in Chrome found problems that 42 passing tests never exercised. The first two were a background-fetch permission issue and unhandled chrome:// pages. The third was a scan that never finished on real sites. Two fixes addressed genuine problems (sequential script fetches with no timeout, then a timeout that stopped at the response headers and left the body read unguarded) but neither changed the symptom.

Instead of a third guess, the extension's Errors panel gave the answer:

chrome://extensions, SentinelScan, Errors
Service worker registration failed. Status code: 15
Uncaught SyntaxError: Cannot use import statement outside a module

Vite had split a shared module into its own chunk, so background.js started with an import. Chrome rejects that unless the manifest declares the worker as a module, so the background script had never run at all. The fix was one line: "type": "module" on background.service_worker. The earlier timeout work stayed in: parallel fetches, a 6-second abort covering request and body, and a 25-script cap.

> talking point

This is the debugging story to tell. Two reasonable fixes in a row did nothing, which was the signal to stop patching and collect evidence. The patched code had never executed. Passing unit tests and a working extension are separate claims, and a packaging problem like a manifest field is invisible to Vitest.

! limitation

The build log does not yet record a clean end-to-end scan of a real site after the manifest fix, and the extension is not on the Chrome Web Store yet (it needs a developer account). The 4.0-bit entropy rule also catches some ids and hashes, which is why those findings are medium severity and worded as a prompt for a manual look.

What it is

An attack-surface inventory for networks you own. Give it hosts, CIDR blocks or ranges and it lists every listening service, names it from the banner it sends, and can compare this week's scan with last week's. Its use cases are defensive: finding a forgotten service, checking that firewall rules block what they should, and spotting expired certificates.

How a scan runs

  • Bounded concurrency. Host and port pairs go onto a jobs channel served by a fixed pool of workers (100 by default). -rate adds a ticker so at most N connection attempts go out per second, for fragile devices like printers and cameras.
  • Probe and identify. A TCP connect with a dial timeout (2s by default) records the handshake latency, then reads a short banner. The banner names the service (SSH, HTTP, SMTP, FTP, MySQL, Redis, VNC and others) and, where it says so, the software version.
  • TLS ports. On 443, 465, 636, 853, 990, 993, 995, 6697 and 8443 it completes a handshake first and records the protocol version, cipher, certificate subject and issuer, validity dates, and whether the certificate is expired, self-signed or mismatched to the host.
  • Change detection. -diff reads an earlier JSON scan, matches results by host and port, and reports what opened, closed or changed. Ports an interrupted scan never reached are reported as closed with a warning, so a partial run cannot pass as a clean one.
  • Guard rails. Banners are reduced to one printable line with all control characters removed before display, and a single scan is capped at 65,536 hosts to prevent accidents.

Sample output (from the README)

$ ./porthawk -t 127.0.0.1,localhost -p 2222,8080,8443,9
porthawk: scanning 2 host(s) x 4 port(s) with 100 workers
HOST       PORT  SERVICE                               TLS   LATENCY
127.0.0.1  2222  ssh (OpenSSH_9.6p1 Ubuntu-3ubuntu13)  -     1.07ms
127.0.0.1  8080  http (SimpleHTTP/0.6)                 -     0.30ms
127.0.0.1  8443  https                                 1.2!  0.80ms
porthawk: 3 open port(s) found in 6ms

The ! after the TLS version marks an expired certificate. A week later, the same command with -diff scan.json reports one service opened, one closed and two upgraded, listing each changed field with its old and new value.

Testing

CI runs go vet, the full test suite, the suite again under -race, and three fuzz targets (FuzzParsePorts, FuzzParseTargets, FuzzCleanBanner). The suite passed again on 2026-10-25 for this page.

> talking point

Fuzz the parsers, not the network code. Port lists, target specs and banners are the three places where untrusted or user-typed text enters the program, so those are the fuzz targets. The rest is covered by unit tests against local listeners, which keeps the suite fast and deterministic.

! limitation

TCP connect scans only. SYN and UDP scanning need raw sockets and root. A service that sends nothing on connect is named by its port number alone, or listed as unknown.

What it is

A read-only analyzer for /var/log/auth.log, /var/log/secure or journalctl output in syslog format. It groups SSH login failures by source IP, ranks the IPs by a score you can check by hand, and calls out any flagged IP that also logged in successfully. It never touches the firewall, never writes to a system file and makes no network calls.

How detection works

  • Parsing. Five sshd line shapes are recognized. Failed password, failed publickey and invalid-user lines count as failures. Preauth disconnects and accepted logins are kept as context columns. Timestamps can be traditional syslog or RFC 3339. Syslog has no year, so a date more than two days in the future is moved back a year, which handles December logs read in January.
  • One attempt, counted once. sshd often writes both an "Invalid user" line and a "Failed password for invalid user" line for a single attempt. The two are merged when they share an IP and source port within 10 minutes, so stuffing runs are not double-counted.
  • Sliding window. Each IP's failures are sorted by time and a window (60 minutes by default) slides over them. The report shows each IP's worst window, while the TOTAL, PREAUTH and ACCEPTED columns cover the whole input.
  • Score and flag rule. Score is failures + 3 × distinct usernames. An IP is flagged when one window reaches 10 failures, 5 distinct usernames or a score of 25, and the REASONS column names which rule tripped.
  • Hostile input. Usernames are chosen by the attacker, so the text report escapes non-printable characters and quotes names containing spaces or commas. Malformed lines are counted and skipped, never fatal.

FLAGGED IPs (3), worst first

1     203.0.113.77           48     12     12

The username weight is why the stuffing run ranks first: 12 attempts across 12 usernames scores 48, while 25 guesses at root scores 28. The sample also hides a slow brute force, 198.51.100.200, guessing once every 7 minutes. It never reaches 10 failures in any 60-minute window (44 over the whole log), and rerunning with --window 2h flags it with 18 failures and a score of 21.

Read-only by design

--blocklist prints the flagged addresses and example iptables and nftables rules, every rule commented out. A flagged IP can be a shared NAT or VPN exit, your own monitoring host, or a colleague with a stale saved password, so applying a block stays a human decision. The README points to the durable fixes instead: disable password authentication and root login, and use keys or MFA.

Testing

46 tests (33 top-level, 13 subtests) cover the parser, analyzer, reports, blocklist and end-to-end CLI runs. go vet is clean, and the suite passed again on 2026-11-01 for this page. The sample log is synthetic and uses only documentation IP ranges (RFC 5737 and RFC 3849).

> talking point

This is the production-shaped successor to Project 5's Python detector: the same per-IP sliding window, plus a username dimension, duplicate-line handling, IPv6, JSON output and a worst-window report. The ACCEPTED column is the signal to lead with. A flagged IP with an accepted login is an incident to investigate, not just an address to block.

! limitation

Batch only: it reads the files it is given and exits, with no live tailing. Grouping is per IP, so an attack spread across many addresses that each stay under the thresholds is not correlated. The thresholds are defaults, not a calibrated baseline, and hostnames in from fields (sshd with UseDNS yes) are counted as malformed rather than resolved.

What it is

A triage tool for the question "is this email real?" Paste the headers from "Show original" (or a single link) and it answers with one of three verdicts, the reasons ranked by severity, and what to do next. It works only on the text it is given: it never opens a mailbox, never fetches a link and never looks up a domain.

How a verdict is built

  • Sender identity. It parses From, Reply-To, Return-Path, Message-ID and the Received chain, then checks whether those agree: a Return-Path on another domain, replies routed to a free mailbox, a display name claiming a brand the address does not belong to, and look-alike or IDN domains checked against 22 commonly impersonated brands.
  • Authentication, read not redone. SPF, DKIM and DMARC come from the Authentication-Results the receiving server already wrote, and each is reported on its own with whether it is aligned to the From domain (relaxed, by organizational domain). Nothing is looked up again.
  • Contradictions. A lower "pass" header that disagrees with the receiving server's own result, a DMARC pass for a different domain, or Received-SPF disagreeing with the results are each a finding, because a sender can add headers but cannot change the ones written after it.
  • Links. Every link in a pasted body is checked lexically: punycode and homographs, credentials before an @, IP-literal hosts in decimal, hex or octal form, shorteners, link text naming a different site than the target, brand-as-subdomain decoys, unusual ports and javascript: or data: schemes.
  • Scoring. Any HIGH finding, or enough smaller ones together, gives LIKELY PHISHING; a couple of warning signs give SUSPICIOUS. Context that is normal for real mail, such as a newsletter whose Return-Path belongs to its email service but which still passes DMARC, is listed as "also noted" and does not count against the message.

The phishing sample produces 10 findings (3 HIGH, 6 MEDIUM, 1 LOW). Both samples are made up for the project and ship as the built-in --demo. Every URL and domain in a real report is printed defanged (hxxps://example[.]com), so nothing in the output is clickable. The demo page is a static showcase of these two runs, not a live analyzer.

Safe by construction, enforced by tests

The safety claims are tests, not promises. One test replaces the socket connect, connection and DNS functions with ones that fail, then runs the demo and a set of tricky links. Another runs the CLI in an empty temporary directory and asserts the directory is still empty afterwards. A third scans the package source for network, mail, logging, database and file-writing code. A fourth checks every report for live links.

Testing

79 pytest tests: 39 for header parsing and spoofing, 27 for URL tricks and 13 for the CLI and the safety rules. Analysis uses only the Python standard library (3.11 or newer), and pytest is the only extra. The suite passed again on 2026-11-04 for this page.

> talking point

"SPF passed" on its own says little. SPF checks the envelope sender, which the attacker chooses, so a phishing email can pass SPF for its own throwaway domain. What protects the address a reader sees is alignment: did SPF or DKIM pass for a domain matching the From header? That is why PhishLens reports all three results separately with alignment, and why it trusts only the topmost Authentication-Results written by the receiving server.

! limitation

It judges only what is pasted. A fully authenticated email from a domain the attacker owns can still be a scam, and the look-alike checks cover a built-in list of brands. Organizational domains come from a small built-in suffix list rather than the full Public Suffix List, and shortened links are flagged but never expanded, because expanding them means visiting them.

What it is

A movie-review app built twice: a vulnerable branch (ports 4000/5173) and a secure branch (4001/5174). Every test is run against the first, then rerun unchanged against the second to prove it now fails.

The four flaws and their root causes

  • SQL injection. The login query was built by concatenating user input into SQL text, so input could change the query's structure and skip the password check.
  • Stored XSS. Review text was saved unsanitized and rendered with dangerouslySetInnerHTML, so markup in a review ran for every visitor.
  • Broken authentication. Passwords were stored and compared in plaintext, and the server returned a user object the client was trusted to keep.
  • Broken access control. The admin endpoint trusted an x-role header the client set itself, and review deletion had no ownership check (an IDOR).

The fixes, and why each closes the whole class

  • Parameterized queries. SQL text goes to MySQL with ? placeholders and values travel separately as data, so input can never become syntax.
  • bcrypt (cost 12) and a signed 2-hour JWT replace plaintext comparison and the honor-system user object.
  • Two XSS layers. sanitize-html strips tags on the server, and the client renders review text as plain text, which React escapes by default.
  • A real requireAuth middleware verifies the JWT and attaches the verified identity. Delete now checks review.author_id === req.user.id || req.user.role === 'admin' from that identity, never from anything the client claims.

Evidence after the fix

same test requests against the secure branch
POST /api/login        (injection test)
HTTP 401 {"success":false,"message":"Invalid credentials"}
GET  /api/reviews/search  (injection test)
[]  (0 rows, no error)
GET  /api/admin/users  -H "x-role: admin"  (no token)
HTTP 401 {"error":"Missing token"}

All 8 before-and-after screenshots come from one scripted Playwright walkthrough (capture_exploits.js and capture_fixes.js). The same script runs on both branches, which is part of the proof that the fixes hold.

> talking point

"Why parameterized queries and not escaping?" Escaping is a blocklist of dangerous characters, and blocklists keep missing cases. Parameterization is structural: the database receives the query and the values through separate channels, so it closes the vulnerability class rather than the inputs you thought to block.

What it is

A small companion to Project 1, built only for this: two endpoints (/login and /search), a seeded MySQL database with 10 users and 10 products, and one Python script per injection class. Passwords are stored as SHA-256 hashes here, a deliberate realism choice that differs from Project 1.

Three classes, three different signals

  • Classic. Input that ends the string early removes the password condition from the login query. Same root cause as Project 1.
  • UNION-based. A product search can be made to return rows from the users table, data the endpoint was never meant to touch.
  • Blind. No rows or errors come back, only a true/false difference in the response (or its timing). The script recovered the first 16 characters of the admin hash this way, matching the real value exactly. Binary search on each character's code took 105 requests in total.

After the fix

With parameterized queries all three return the same empty result: 0 rows on the UNION test, an empty prefix on the blind test and no timing difference. The input is inert data with no query structure left to change.

> talking point

Blind injection is the one to explain slowly. It shows why "we never display database errors" is not a defense: a single yes/no signal, asked enough times, still leaks exact values. Binary search needs about log2(charset) requests per character instead of one per possible character, which is why it took 105 requests for 16 characters. The only real fix is the structural one.

What it is

Fit a baseline distribution to normal traffic, then flag deviations with a formal hypothesis test: the one-sample z-test from intro stats, pointed at security telemetry instead of a survey sample.

Why the traffic is simulated

Live capture needs root (macOS BPF devices are root-only), which the build environment did not have:

$ checking live capture
>>> scapy.all.sniff(timeout=5, count=20)
Scapy_Exception: Permission denied: could not open /dev/bpf0.

So capture.py builds real Scapy packet objects (sizes come from len(bytes(pkt)), not constants) without putting them on the wire. Baseline arrivals follow a Poisson process. The simulated scan is a 5-second burst of about 400 small SYN packets, and the simulated exfiltration is a 15-second run of near-MTU outbound payloads.

The method

The baseline is fit on the first 300 seconds only, which are normal by construction. Everything from t=300s on is held out. Each feature gets its own distribution:

  • packet_count is Poisson, tested with z = (x - λ) / √λ.
  • unique_dst_ports and mean_pkt_size are Normal, fit by MLE with scipy.stats.norm.fit and justified by the CLT.

A window is flagged if any |z| exceeds 2.576 (two-tailed, α = 0.01). Three tests per window inflate the false-positive rate to about 1 - 0.99³ ≈ 3%, accepted on purpose because a missed attack costs more than an extra review.

Held-out results

metricvaluefrom
Recall100.0%20 of 20 attack windows caught
Precision80.0%20 of 25 flagged windows were attacks
False positive rate2.8%5 of 180 normal windows; theory predicted about 3%
F1 score0.889TP=20, FN=0, FP=5, TN=175

Both attacks were caught on their first window: t=300s for the scan (zports = +73.36) and t=330s for the exfiltration (zpkts = +12.34). Precision is the complement to the recall headline: 1 in 5 alerts is a false alarm, the visible cost of OR-ing three tests.

! limitation

The simulated attacks make no attempt to blend in (no slow scanning, no timing jitter, no size padding), so an adaptive attacker could likely evade this exact detector. The three tests also ignore feature correlation. A Bonferroni correction or Hotelling's T² would raise precision at some cost in recall.

> talking point

"Why a z-test and not chi-square?" Chi-square compares a whole distribution with an expected one. The question here is narrower: is this one window implausibly far from a fitted mean? That is a one-sample z-test.

Two tracks, kept separate

Pipeline

The brute-force detector

A two-pointer sliding window per source IP, O(n) per IP, over OpenSSH-style log lines. A flat count cannot tell a burst from background noise: the sample log has three IPs failing logins, and only one clusters tightly enough to cross the threshold.

$ python3 log_bruteforce_detector.py sample_data/auth.log
Parsed 11 failed-login events. Window: 300s | Threshold: 5
ALERT  203.0.113.9: 8 attempts in 300s window (22:30:01 -> 22:30:15)

The password auditor

Checks length, character classes, common-password membership, sequential runs and repeats, then turns estimated entropy into crack time under three threat models, because what attacks the hash matters as much as the password: unsalted MD5 offline (about 10¹⁰ guesses/s), bcrypt cost 12 offline (about 2×10³/s), and a rate-limited login form (about 10/s).

A company built for its sector

The assessment covers Meridian Environmental Logistics, built to be realistic for logistics and environmental services rather than a generic template. A company that reports waste and disposal data to regulators has a risk most templates miss: data integrity tied to its operating license, not just to money or uptime. Two of the ten risks exist because of that.

Inherent vs residual

Every risk is scored twice: assuming no controls (inherent) and with today's controls (residual). That turns a list of bad things into a prioritization tool.

riskinherentresidualwhy the gap
R-01 Ransomware on ERP/finance20/25 critical10/25 highBackups and AV already partly mitigate it
R-02 BEC leading to a fraudulent wire15/25 high10/25 highManual callback checks, inconsistently followed

That gap drives the roadmap: close R-02 first with dual approval on wires, and test R-01's untested restores, instead of spending more on a risk that is already partly covered.

Every policy cites a risk

Each control under Identify, Protect, Detect, Respond and Recover names the risks it answers, for example PR.AC: Enforce phishing-resistant MFA on ERP/finance [R-01, R-02, R-09].

How it was built

Generated with docx in Node, so the Word tables and the CSV exports come from one data source and cannot drift apart. That surfaced a layout bug: the 12-column register needed 13,830 DXA against a 9,360 DXA portrait page. The fix gave that table its own landscape section (12,960 DXA) instead of cramming columns.

> talking point

This project leans on the Management Engineering background. GRC teams need people who can read the technical risk correctly, such as why R-01's residual score sits below its inherent score, and explain it in plain language.

Built on Project 4 by import

The capstone imports Project 4's log_generator, siem_ingest and detection_rules modules instead of copying them. It adds one event type (data_exfil) and one column (bytes_transferred), and Project 4's own pipeline was rerun afterwards with identical results.

The simulated intrusion

  1. Initial access (T1110, T1078): 22 password guesses against internet-facing web01, ending in a valid login as employee rpatel.
  2. Lateral movement (T1021.004): the same account moves from web01 to app02 and db01 over SSH.

> talking point: detection-engineering judgment

The correlation rule fires only when all three stages tie back to the same identity in causal order, then raises one chain alert instead of three noisy ones. It trades a little latency for an alert an analyst can act on, which is the difference between a SIEM that cries wolf and one people trust.

! limitation

The lateral-movement rule is identity-scoped: it relies on stage 1 having flagged rpatel. A production version would also baseline each account's normal hosts, so first-time access to a new host is flagged even without an earlier brute-force alert.

What it is

A scanner that reads Terraform .tf files and flags common AWS misconfigurations before the infrastructure is ever applied. It never calls the AWS API and needs no account, so every result is reproducible at no cost. It follows the same before-and-after pattern as Project 1: a deliberately vulnerable Terraform set and a fixed one.

Five rules

CLOUD-S3-PUBLIC-ACLhighBucket ACL is public-read or public-read-write

CLOUD-IAM-WILDCARD-ADMINhighPolicy allows Action: "*" on Resource: "*"
CLOUD-STORAGE-UNENCRYPTEDmediumRDS instance or EBS volume with encryption off

The exit code is 1 when findings exist and 0 on a clean scan, so it can gate a CI pipeline as-is.

> talking point

Each of these misconfigurations is one line of Terraform and easy to miss in review. A check that runs on every change and fails the build turns a reviewer's memory into a gate. It also fills the portfolio's cloud gap: everything else is on-prem.

! limitation

The parser (scanner/hcl_lite.py) is scoped on purpose: resource blocks, flat attributes, one level of nested blocks and heredocs, but no for_each, dynamic blocks, modules or interpolation functions. Production Terraform would need a real parser such as python-hcl2. The rules echo CIS AWS Foundations themes but are not certified CIS mappings.
