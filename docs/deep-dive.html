01AppSec · Flagship

Vulnerable-to-Secure Web App

Fully verified React (Vite) Express MySQL 5.7 bcrypt + JWT
Resume line

Built and exploited a full-stack React/Node/MySQL application demonstrating 4 OWASP Top 10 vulnerabilities, then remediated each with parameterized queries, output sanitization, bcrypt password hashing, and JWT-based authorization — documenting the full attack-and-fix lifecycle with live exploit scripts and screenshots.

What it is

A movie-review app — the same React/Node/MySQL shape as prior coursework — built twice: a vulnerable branch (port 4000/5173) and a secure branch (port 4001/5174), so every exploit could be run against the first and then re-run, unmodified, against the second to prove it now fails. Four real vulnerabilities, not toy versions of them.

How each vulnerability works

1 — SQL injection. The login query concatenated user input directly into SQL text: `... WHERE username = '${username}' AND password = '${password}'`. The payload admin' -- closes the string early and comments out the password check, so the database runs WHERE username = 'admin' with no password condition at all.

$ curl -X POST :4000/api/login (real output)
POST /api/login {"username":"admin' -- ","password":"anything"}
{"success":true,"user":{"id":3,"username":"admin","role":"admin"}}

2 — Stored XSS. Review text was stored with zero sanitization and rendered with dangerouslySetInnerHTML. A posted <img src=x onerror="..."> payload fires the moment the page loads for any visitor — captured live, changing document.title to XSS-EXECUTED and injecting visible text into the DOM.

3 — Broken authentication. Passwords were stored and compared in plaintext, with no session mechanism — the server just handed back a user object the client was trusted to keep honestly.

4 — Broken access control. Two instances: /api/admin/users "checked" authorization by reading an x-role header the client set on itself, and DELETE /api/reviews/:id had no ownership check — any client could delete anyone's review by id (a classic IDOR).

The fixes, and why they close the whole class

  • Parameterized queries — the SQL text is sent to MySQL fully-formed with ? placeholders, then values are sent separately as data. The database never re-parses them as SQL, so a quote, a comment marker, or a UNION keyword in the input just becomes an inert value to compare against — not a way to change the query's structure.
  • bcrypt (cost 12) + a signed, 2-hour JWT — replaces plaintext comparison and the honor-system user object with a cryptographic session the server actually verifies.
  • Two independent XSS layers — sanitize-html strips all tags server-side and the client renders review text as plain text (React escapes by default) instead of raw HTML — defense in depth, not one gate.
  • A real requireAuth middleware — verifies the JWT signature and attaches the verified role/id to the request; delete now checks review.author_id === req.user.id || req.user.role === 'admin' from that verified identity, never from anything the client claims.

Real evidence — same payload, before and after

$ same admin' -- payload against the fixed server
POST /api/login {"username":"admin' -- ","password":"anything"}
HTTP 401 {"success":false,"message":"Invalid credentials"}
GET /api/reviews/search?q=x' UNION SELECT ... --
[]  (0 rows, no error)
GET /api/admin/users -H "x-role: admin"  (no token)
HTTP 401 {"error":"Missing token"}

All 8 exploit/fix screenshots were captured with a scripted Playwright walkthrough (exploits/capture_exploits.js and capture_fixes.js) rather than taken by hand — the same script runs identically against both branches, which is itself part of the proof that the fix generalizes.

Talking point

If asked "why parameterized queries and not just escaping quotes" — escaping is a blocklist against known-dangerous characters, and blocklists are inherently incomplete (encoding tricks, alternate comment syntaxes, etc. keep finding gaps). Parameterization is an architectural fix: user input structurally can never become SQL syntax, because the database receives the query and the values through two separate channels. It closes the entire vulnerability class, not just the payloads you thought to block.

02AppSec · Focused Lab

SQL Injection Deep Dive

Fully verified Express MySQL Python requests
Resume line

Demonstrated and remediated classic, UNION-based, and blind SQL injection against a live MySQL-backed Node.js application using automated Python exploit scripts; root-caused the flaw to string-concatenated queries and secured it with parameterized queries, verifying all three attacks failed post-fix.

What it is

A smaller, purpose-built companion to Project 1 — two endpoints (/login, /search), a seeded MySQL database with 10 users (passwords stored as SHA-256 hashes, not plaintext — a different, deliberate realism choice from Project 1) and 10 products, and three different classes of SQL injection run against it, each with a dedicated Python script.

Three techniques, three different oracles

Classic (comment truncation). Same mechanism as Project 1's bypass — admin' -- strips the trailing AND password_hash = '...' clause entirely.

UNION-based. Run as a real attacker would: first discover the column count by trying UNION SELECT NULL, then NULL,NULL, and so on until the database stops erroring — this alone reveals the target table has 5 columns without ever seeing the source. Then swap the NULLs for real columns pulled from an entirely different table (users), so its data rides back through a product-search response that was never meant to touch it.

$ python3 02_union_based.py (real output, excerpt)
[1] Discovering column count via UNION SELECT NULL,NULL,...
    n=1..4 -> HTTP 500 (column count mismatch)
    n=5  -> HTTP 200 (matches!)
[2] Exfiltrating users table via UNION
    admin   admin   87af2904434a87cc9c6954a3c84f4f286f141e12c338beb06d2ca01b8f9f3322

Blind (boolean + time-based). No error, no leaked rows this time — just one true/false bit per request. A boolean oracle (... OR <condition> -- , testing count: 10 vs count: 0) recovers each hash character via binary search on its ASCII code rather than testing all 16 hex values linearly — roughly 6–7 requests per character instead of up to 16. A time-based oracle (OR IF(condition, SLEEP(0.1), 0)) confirms the same bits with a stopwatch instead of a response body, for when even the row count is hidden.

$ python3 03_blind_injection.py (real output, excerpt)
pos  char  requests
1    '8'   7
2    '7'   6
...
Extracted prefix: 87af2904434a87cc
Total requests: 105  |  Elapsed: 0.13s
pos=1 correct-guess -> 1.03s (SLOW=TRUE)   wrong-guess -> 0.00s

The blind-extracted prefix (87af2904434a87cc) matches the first 16 characters of the real hash exactly — recovered without that hash ever appearing directly in a response body, purely from true/false and fast/slow signals.

Post-fix: all three fail identically

The parameterized version returns the same shape of "no data" for all three techniques — 0 leaked rows on UNION, an empty extracted prefix on blind boolean, and zero timing signal on blind time-based — because the injected condition is now inert text with nothing left to inject it into.

Talking point

The blind technique is the one worth being able to explain slowly in an interview, because it's the least intuitive: you're recovering exact byte values from a system that never shows you any data at all, using nothing but a binary yes/no signal repeated enough times. Being able to walk through why binary search on the ASCII code beats linear character guessing (log₂(charset) vs. charset requests per position) is a good signal that you understand the technique rather than having copied a script.

03Data / Detection

Network Traffic Anomaly Detector

Fully verified Python Scapy scipy.stats matplotlib
Resume line

Developed a Python-based network anomaly detector applying statistical hypothesis testing (z-score baseline deviation across Poisson- and Normal-fitted traffic features) to identify port-scan and data-exfiltration patterns, achieving 100% detection recall with a 2.8% false positive rate on a labeled synthetic dataset (500 one-second windows, held-out evaluation).

What it is

The project explicitly built to prove a statistics background is a real security asset: fit a baseline distribution to "normal" traffic, then flag deviations with a formal hypothesis test — the same one-sample z-test framework used against a population parameter in intro stats, pointed at security telemetry instead of a survey sample.

Why the traffic is simulated, stated plainly

Live packet capture needs root (macOS BPF devices are root-only), which this environment doesn't have — confirmed directly, not assumed:

$ verifying capture is unavailable
>>> scapy.all.sniff(timeout=5, count=20)
Scapy_Exception: Permission denied: could not open /dev/bpf0.

So capture.py uses Scapy to construct real packet objects (IP()/TCP()/UDP() layers) — byte sizes come from len(bytes(pkt)) on genuine packet structures, not hand-picked constants — they're just never put on the wire. Baseline arrivals follow a Poisson process (the standard model for aggregate, memoryless network traffic); a simulated port scan sends ~400 small SYN packets across sequential ports in a 5-second burst, and a simulated exfiltration pushes a sustained 15-second burst of near-MTU outbound payloads.

The statistical method

The baseline is fit on the first 300 seconds only — pure normal traffic by construction — and everything from t=300s onward (both attacks, plus untouched normal windows) is held out and never used for fitting. Two distribution families, chosen per feature rather than applied blindly:

  • packet_count → Poisson (arrivals are Poisson by construction, so counts per fixed window are too); test statistic z = (x − λ) / √λ.
  • unique_dst_ports, mean_pkt_size → Normal, fit via scipy.stats.norm.fit (MLE), justified by the CLT since these are aggregates over many packets per window.

A window is flagged if any of the three |z| exceeds the two-tailed critical value at α = 0.01 (zcrit = 2.576). Running three tests per window is a multiple-comparisons problem — under independence, the naive false-positive rate inflates to roughly 1 − 0.99³ ≈ 3%. That's stated as a deliberate trade-off (missing an attack is worse than an extra analyst review), not hidden as an oversight.

Real results — held-out evaluation

MetricValue
Attack windows (t ≥ 300s)20
Normal windows (t ≥ 300s)180
Detection rate (recall)100.0%
False positive rate2.8% (theory predicted ≈3%)

Both attacks were caught on their very first window — t=300s for the scan (zports = +73.36), t=330s for the exfiltration (zpkts = +12.34) — with zero missed attack windows and the empirical false-positive rate landing almost exactly where the multiple-comparisons math predicted it would.

Honest limitation

The port scan and exfiltration patterns aren't evasive — no slow/low-and-slow scanning, no timing jitter, no size padding toward the baseline mean. A real attacker adapting to this exact detector could plausibly evade it. Feature correlation is also ignored (three independent tests instead of a joint/multivariate one), which is what actually drives the false-positive inflation — a Bonferroni correction or Hotelling's T² would trade recall for a lower FPR.

Talking point

"Why z-score and not chi-square" is a fair question and has a real answer: chi-square tests whether an entire empirical distribution matches an expected one — useful for comparing whole histograms. Here the question per window is simpler: "is this one observation implausibly far from a known/fitted population mean?" — that's a one-sample z-test, not a goodness-of-fit problem.

04Blue Team

Home SOC / SIEM Lab

Track A verified · Track B documented Python SQLite Flask ELK (spec only)
Resume line

Built a home SOC lab with a Python-based log ingestion pipeline and rule-based SIEM alerting engine (SQLite + sliding time-window detection); generated and detected simulated SSH brute-force and port-scan attacks end-to-end, verified via a live Flask dashboard, and produced a full incident report grounded in the actual pipeline output.

Two tracks, clearly separated

Track A — a Python + SQLite SIEM, actually run in this environment; every number below is real. Track B — a full ELK-stack docker-compose.yml for the production-equivalent path, written to spec but never started, because this environment has no docker binary. The README says exactly that rather than blurring the two.

Pipeline

log_generator.py writes a syslog-style auth.log mixing normal SSH logins from 6 simulated accounts with two embedded attacks. siem_ingest.py regex-parses every line into a structured SQLite table (and reports, rather than silently drops, anything it can't parse). detection_rules.py applies two independent sliding-window rules: ≥8 failed logins from one IP in 5 minutes (brute force) and ≥8 distinct ports from one IP in 30 seconds (port scan). dashboard.py serves the result read-only over Flask.

Both attacks were flagged with zero false positives among the 91 legitimate logins — including several innocuous single-retry-then-succeed cases baked into the baseline traffic specifically to test that. The dashboard was actually started and hit with real requests (/healthz → 200, /api/alerts returned both alerts as JSON, /api/timeline returned correct per-hour buckets) before being stopped — nothing was left running.

Honest limitation

Detection thresholds are justified against published tool behavior and common SIEM defaults, not calibrated against a real production traffic baseline — a real deployment would need that calibration to control its own false-positive rate. Track B has never been run, let alone tested, here.

Talking point

Project 5's brute-force detector uses the identical sliding-window algorithm as this SIEM's detection rule, just as a smaller standalone tool. Being able to point out that connection — same technique, two different scales, one imported into the capstone below rather than rewritten — is a good way to show the portfolio isn't 8 disconnected exercises.

05Tooling

Security Automation Scripts

Fully verified Python (stdlib only) unittest
Resume line

Wrote Python security automation tools — an SSH auth-log brute-force detector using a sliding-window algorithm, and a password-policy auditor estimating offline crack time across three threat models (fast hash, bcrypt, rate-limited login) — with unit tests covering the core detection algorithms.

The brute-force detector

A classic two-pointer sliding window per source IP — O(n) per IP, not a naive re-scan — over OpenSSH-style log lines. The point of the sliding window over a flat grep -c | wc -l count is that it can tell a burst from background noise: the sample log has three IPs failing logins, but only one clusters tightly enough in time to cross the threshold.

$ python3 log_bruteforce_detector.py sample_data/auth.log (real output)
Parsed 11 failed-login events. Window: 300s | Threshold: 5
ALERT  203.0.113.9: 8 attempts in 300s window (22:30:01 -> 22:30:15)
       usernames tried: admin, administrator, oracle, postgres, root, ubuntu

The password auditor

Checks length, character-class diversity, common-password membership, sequential runs, and repeated-character runs, then converts estimated entropy into crack time under three different threat models — because what's attacking the hash matters as much as the password itself: an unsalted-MD5 offline crack (~10¹⁰ guesses/sec), a bcrypt cost-12 offline crack (~2×10³ guesses/sec), and a rate-limited login form (~10 guesses/sec).

Password (masked)EntropyFast hashbcrypt
p******d37.6 bits10.4 seconds1.7 years
c***********************e117.5 bits (fails policy)3.75×10¹⁷ yrs1.88×10²⁴ yrs
7*************************!177.4 bits (passes)3.97×10³⁵ yrs1.98×10⁴² yrs

The middle row is correcthorsebatterystaple — the XKCD-936 password. It has more entropy than several passwords that pass the policy, but still fails, because it's all lowercase. That's included on purpose: NIST SP 800-63B's current guidance actually leans toward entropy/length over composition rules, and this is a genuine, defensible tension worth being able to discuss rather than a bug.

Talking point

Ten unit tests cover both scripts' core algorithms — including a test that a burst is flagged but the same total count spread across hours is not, which is really a test of the sliding-window logic itself, not just "does the script run."

06GRC

GRC Risk Assessment (NIST CSF)

Fully verified NIST CSF docx (generated)
Resume line

Authored a NIST CSF-aligned cybersecurity risk assessment for a simulated mid-size organization: a 12-asset inventory, a 10-item risk register scoring both inherent and residual risk, and a full security policy framework mapped to all five NIST CSF functions, each control traced to a specific identified risk.

Why the fictional company isn't generic

The assessment covers Meridian Environmental Logistics, built to be realistic for the logistics/environmental-services sector rather than a generic template company. That detail matters: an organization that reports waste-volume and disposal data to regulators has a risk category most templates don't surface — data integrity tied directly to an operating license, not just to money or uptime. Two of the ten risks in the register exist specifically because of that.

The scoring model — inherent vs. residual

Every risk is scored twice: once assuming no controls exist (inherent), and once accounting for what's actually in place today (residual). That distinction is what turns a risk register from a list of bad things that could happen into an actual prioritization tool:

RiskInherentResidualWhy the gap
R-01 Ransomware on ERP/finance20/25 Critical10/25 HighBackups + AV already partially mitigate it
R-02 BEC → fraudulent wire15/25 High10/25 HighManual callback verification, inconsistently followed

That gap is the actual argument for the roadmap: R-01's residual risk is already lower than R-02's because backups exist — so the near-term roadmap prioritizes closing R-02 (dual-approval on wire transfers) and testing R-01's untested restores, rather than throwing more budget at something already partly mitigated.

Every policy traces to a risk ID

Section 5 doesn't list generic NIST CSF best practices — each bullet under Identify / Protect / Detect / Respond / Recover cites the specific risk(s) it addresses, e.g. PR.AC: Enforce phishing-resistant MFA on ERP/finance... [R-01, R-02, R-09]. It reads as a direct response to the assessment, not a copy-pasted checklist.

How it was actually built

Written programmatically with docx (Node) rather than by hand in Word, so the Word tables and the CSV exports derive from one shared data source and can't drift out of sync. Building it surfaced a real layout bug worth mentioning: the 12-column risk register table's widths summed to 13,830 DXA against a 9,360 DXA portrait content width — it silently would have overflowed the page. The fix was giving that one table its own landscape-oriented document section (12,960 DXA available) rather than cramming or truncating columns.

Talking point

This is the project that leans hardest on a Management Engineering background rather than pure technical skill — and it's worth framing that way directly: GRC roles are chronically short on people who can also read the technical risk correctly (e.g., why R-01's residual score is lower than its inherent score, in plain language) rather than just filling in a template.

08Blue Team · Capstone

Capstone: Detection & Response

Simulation verified · single deterministic run Python SQLite MITRE ATT&CK
Resume line

Simulated and detected a multi-stage attack chain (initial access → lateral movement → exfiltration) against a home-built SIEM pipeline, mapped to MITRE ATT&CK (T1110, T1078, T1021.004, T1041) with correlation logic tying all three stages to one identity, producing a full incident response report with timeline, root cause, and remediation recommendations.

Built on Project 4 by import, not duplication

This capstone imports Project 4's log_generator, siem_ingest, and detection_rules modules directly rather than copying their logic. It extends the ingestion schema with one new event type (data_exfil) and one new column (bytes_transferred) — backward-compatibly enough that Project 4's own pipeline was re-run after the change and produced identical results, confirming nothing broke.

The attack narrative

  1. Initial access (T1110 Brute Force → T1078 Valid Accounts) — 22 password-guessing attempts against internet-facing web01, mixing default usernames with one real employee account (rpatel) obtained via simulated OSINT, ending in a successful login.
  2. Lateral movement (T1021.004 Remote Services: SSH) — using the now-valid rpatel credentials, the attacker pivots from web01 to app02 and db01.
  3. Exfiltration (T1041 Exfiltration Over C2 Channel) — a ~812 MB outbound transfer from db01, deliberately sent over port 443 to blend in with normal HTTPS egress.

Total simulated dwell time: 13.1 minutes, end to end.

Talking point — the part that shows detection-engineering judgment

The correlation rule doesn't fire on any single stage alone — it requires all three to tie back to the same identity, in causal order, before raising one chain-level alert instead of three independent noisy ones. That's a real, defensible design choice: it trades a small amount of detection latency (you wait for the full chain) for a much lower-noise alert an analyst can actually act on — the difference between a SIEM that cries wolf and one an analyst trusts.

Honest limitation

The lateral-movement rule is intentionally identity-scoped — it trusts that stage 1 already flagged rpatel as compromised, rather than being fully anomaly-based. A production version would also want a baseline of each account's normal host-access pattern, to flag first-time access to a new host even without a prior brute-force alert triggering first.

09Cloud Security · IaC

Cloud / IaC Misconfiguration Scanner

Fully verified Python (stdlib only) Terraform 5 rules, 9 unit tests
Resume line

Built a Python static-analysis tool that parses Terraform IaC and flags AWS misconfigurations (public S3 ACLs, world-open SSH/RDP security groups, wildcard IAM admin policies, unencrypted RDS/EBS storage) across 5 rule checks; verified against a deliberately vulnerable Terraform set (7/7 findings correctly flagged) and a remediated set (0 false positives), with 9 passing unit tests covering the parser and rule logic.

Why this one exists

Projects 1-8 are all on-prem: a web app, a database, a network, a host. None of them touch public cloud, which is where a large share of real-world misconfiguration incidents actually start — a permissive S3 ACL or a wildcard IAM policy shipped in Terraform, applied once, and left running. This project closes that gap with the same bar as everything else here: something real, run against real fixtures, with the output actually captured.

How it works

It's pure static analysis over local .tf text — no AWS account, no API calls, no cost, fully reproducible by anyone who clones the repo. A scoped parser (hcl_lite.py) walks Terraform source with brace-depth counting to pull out resource blocks, their flat attributes, one level of nested blocks (like repeated ingress { } blocks on a security group), and heredoc string bodies — handled specially so embedded JSON braces in an IAM policy don't break the outer brace count. Five rule functions then pattern-match against the parsed structure: public S3 ACLs, SSH/RDP open to 0.0.0.0/0, IAM statements with Action: "*" + Resource: "*", and unencrypted RDS/EBS resources.

Real scan output

9 unit tests cover the parser (flat attributes, repeated nested blocks, heredoc-with-embedded-braces) and the rules (each vulnerable fixture flagged, the fixed set clean, plus edge cases like public-read-write and a correctly-scoped IAM policy that should not fire) — all passing.

Talking point — why a hand-rolled parser instead of a library

A real production scanner would use python-hcl2 or a proper HCL grammar rather than brace-counting regex. Writing the scoped version by hand was the point here: it forces understanding of exactly what breaks a regex-based approach (embedded JSON braces inside a heredoc policy string being the sharpest example) rather than treating parsing as a solved problem a library hides.

Honest limitation

hcl_lite.py's own docstring states its scope directly: it handles resource blocks, flat attributes, one level of nested unlabeled blocks, and heredocs — not for_each, dynamic blocks, modules, or interpolation functions. That's sufficient for every fixture in this project, but pointing it at arbitrary production Terraform would need a real parser first. The 5 rules are also informally mapped to CIS AWS Foundations Benchmark and AWS Well-Architected themes, not claimed as certified/official control citations.
